## 2. CLS — the one finding that needs the most care, not the least

### The core discrepancy

| | Baseline run | Latest run |
|---|---|---|
| Mobile CLS score | 0.823 (fails — "poor," threshold is 0.25) | 0 (passes) |
| `footer.tsx:33` (the audit's own named root cause) | `height={0}` | `height={0}` — **re-verified today, byte-identical, unchanged** |

The Lighthouse score flipped from failing to passing. The code responsible for the failure did
not change. Both facts are independently confirmed, not inferred.

### Root cause

```tsx
// src/components/layouts/footer.tsx:29-35
<MuImage
  src="/assets/logo.webp"
  alt="µLearn Logo"
  width={180}
  height={0}          // ← the bug: reserves zero vertical space before load
  className="object-contain"
/>
```

`public/assets/logo.webp` is natively 1578×424px. At `width={180}`, the correct proportional
height is `180 × 424 / 1578 ≈ 48.4` → **`height={48}`**. Next's `<Image>` uses the declared
`width`/`height` to reserve layout space before the image itself has loaded. With `height={0}`,
the footer — present on every route — renders with zero reserved height, then visibly jumps
open once the logo image finishes loading. In the baseline run, PageSpeed Insights' own
"Layout shift culprits" audit attributed **100% of the 0.823 score to this exact element** —
that's the tool's own element-level attribution, not a guess.

### Why the score reads 0 now, with the bug still present

CLS is scored by watching for unexpected layout movement inside a bounded observation window
tied to page load and network-idle timing. The footer sits below the fold on first paint, so
whether its late image-load-triggered jump gets *counted* depends on whether that jump lands
inside or outside the window — which itself depends on exact network-timing jitter that
differs between two separate lab runs (different time of day, different PSI worker machine,
Slow-4G-simulated throttling variance). **This is measurement-timing luck, not a fix.** The
underlying reserved-space bug is unconditionally present in every page load; it will very
plausibly fail again on the next PSI run, or for a real visitor whose own network conditions
land the shift inside their browser's counted window.

### Why this outranks the other two lucky-score findings

Two other findings in this pass also turned out to be measurement artifacts rather than real
fixes (`link-name` passing only because `backto-top.tsx` doesn't render until scroll; Agentic
Browsing's score partly riding on this same CLS flip). Both of those are low-consequence — a
missing label on one icon-only link is a narrow a11y gap. CLS is categorically different: it's
one of Google's three Core Web Vitals, it's what Chrome UX Report field data will independently
re-measure once this site has real traffic, and 0.823 sits deep in "poor" territory. **Part of
the mobile Performance score's 45→70 jump is riding on this same coincidence** — CLS factors
directly into Performance's weighted formula, so until this is fixed for real, some of that
25-point gain should be treated as provisional, not banked.

### The fix

```diff
- height={0}
+ height={48}
```

One line, in `footer.tsx:33`. Zero visual change — the image already renders at its correct
aspect ratio once loaded regardless; this only fixes the space reserved *before* load.

### A second, unmeasured instance of the same bug

`src/features/community-partners/components/community-partners-view.tsx:66-67` has the
identical `width={0} height={0}` pattern, confirmed present today, on the `Coding Workshop
Animation` GIF. This route (`/partners/community-partners`) was never covered by this
Lighthouse run — PSI only measured `/`. Not counted in the 0.823 score above, but the same bug
shape; worth its own CLS check once the footer fix is confirmed, since `width=0 height=0`
combined with CSS-driven sizing may need a different fix shape than the footer's (numeric-only)
case.

### Verification plan — don't repeat this pass's mistake

A single passing PSI run is not sufficient evidence of a fix, given the finding above.

1. Apply `height={48}`.
2. Re-run PSI mobile **at least twice**, ideally hours apart, and confirm CLS holds at (or
   very near) 0 across runs — one clean run doesn't distinguish "fixed" from "got lucky again."
3. Cross-check with Chrome DevTools' Performance panel on a throttled connection — it shows
   layout-shift regions directly, a stronger signal than one lab score.
4. Once confirmed, assess `community-partners-view.tsx`'s instance separately.

identically, in both categories. Fixing item 2 is therefore the only remaining lever for both
Accessibility's `button-name` and Agentic Browsing's one open audit.
